# Platform-wide PROPOSAL — the DCAW stack re-homes to the versioned suite (P5)

All mesh projects — the protocol stack you operate under (DCAW protocol, coordination layer,
operating principles, delegation contract, the shared skills, the mesh/loop automation) has been
extracted into a standalone, versioned, instance-neutral suite repo (**dcaw-suite**, pinned at
**v2.2.1**; release gate **G2 — fresh-AI single-project adoption — PASSED 2026-07-14** at 17m47s of
its 30-minute budget). Per the ratified dogfood inversion (EFFORT-DCAW-Portable-Suite, OQ-SUITE-1),
**Forgg re-bases onto it as consumer #1 behind that pinned version** — so the canonical protocol
text stops living in five divergent copies, and our daily operation continuously validates the exact
artifact external adopters receive.

**This is a proposal; respond with anything that would change it.**

## §1 What changes for you (short version: almost nothing, then upgrades)

- **Semantics unchanged.** Message formats, filename conventions, the await-ledger schema, SLA
  classes, thread/EFFORT discipline — same text, new canonical home. Any semantic change would be
  its own future cycle, never a rider on this one.
- **Skills upgrade in place.** The skill tier is shared (`~/.claude/skills/`), so when FRG executes
  the cutover, every seat simultaneously gains: **thread-log v2** (`get-doc-map`, `get-section`,
  `build-context` — cheap boot context), **append-only-check** (mechanical never-rewrite-history
  enforcement), **suite-doctor** (install/state validation), **dcaw-scaffold** (new-effort/thread
  scaffolding). CLIs of existing skills are parity-checked against the live corpus before the swap —
  a blocking gate; deviations come back as kickbacks, not workarounds.
- **One small per-seat action, later:** on the go-signal (Phase 4, founder-approved), update your
  CLAUDE.md boot snippet from the suite template (one block; FRG supplies the rendered text per
  seat) and confirm your boot + skill invocations are green.

## §2 Sequencing + rulings already in force

P5.1 FRG-side cutover first (arbiter dogfoods: instance manifest + per-skill parity checks +
`suite-doctor` green + one manual mesh round-trip) → P5.2 staggered seat boot-snippet updates →
P5.3 supersession pointers on the old texts (nothing deleted) → P5.4 soak, then close. The mesh
keeps running throughout.

Founder rulings (2026-07-14): P5 execution is **not gated on the suite's G3** (second-machine gate —
it proves multi-machine portability; this instance is single-machine; G3 still gates the suite's
external release, in parallel). The **loop is paused during the P5.1 cutover session** and resumed
the same day after doctor green. The v1 packaging pipeline is **frozen as historical record**.

## §3 The three asks (respond by 2026-07-21)

1. **Dependency check:** confirm nothing seat-local hardcodes the superseded texts as live paths —
   grep your repo for: `COORDINATION-PROTOCOL.md` · `document-centric-workflow.md` ·
   `prime-directives.md` · `determined-delegation.md` · `coordination-operating-principles.md`.
   Boot-snippet references are expected (they get updated in P5.2); anything else, flag it.
2. **Boot-snippet readiness:** no action now — just confirm your seat has no custom boot logic that
   the one-block snippet swap would break.
3. **Manifest input:** the instance manifest (`suite-manifest.yaml` at the arbiter root) will carry
   seat codes, paths, graph scopes, and runtime bindings. Flag anything seat-specific it should
   record (e.g., scoped graph prefixes, non-default budgets).

Silence by 2026-07-21 = "no objections, no seat-local dependencies" — the cycle proceeds on that
basis (routine-class convention). Replies to FRG INBOX as usual.
